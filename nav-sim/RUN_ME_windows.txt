KESTREL - one binary for the three things this project can demonstrate
=====================================================================

BUILDING IT
    cmake -B build -DCMAKE_BUILD_TYPE=Release
    cmake --build build --config Release

That produces exactly ONE executable: build\Release\kestrel.exe. The live
sim, the object-lock tracker and the planner baselines are all compiled into
it -- there is no voxel_live.exe or voxel_sim.exe to keep beside it any more.

If the configure step fails it will be on OpenCV, which is the only hard
dependency. Point CMake at your install and try again:

    cmake -B build -DOpenCV_DIR=C:/opencv/build -DCMAKE_BUILD_TYPE=Release

Only core, imgproc and imgcodecs are required. highgui (windows) and videoio
(video files) are each optional and each prints a status line saying whether
it was found; without them the sim is headless and `track` takes an image
sequence instead of a video, which is the better regression input anyway.

Double-click  kestrel.exe        a menu over all of it

  kestrel track --box X Y SIZE --csv out.csv frames*.png
        object lock over recorded frames or a video. --box designates the
        target on the FIRST frame; without it the centre is used, which is
        only right if that is where the target is. Prints lock rate and
        writes a per-frame state timeline.

  kestrel bench --worlds forest maze --seeds 101 108
        the non-RL path-planner baselines, through the SAME environment a
        learned policy uses. These are the numbers a policy has to beat.

  kestrel sim [args...]
        the live voxel sim, running IN this process. Takes voxel_live's
        flags unchanged: --replay FILE.kdr, --live, --rs-check, --sim.

  kestrel train [args...]
        RL training. This is the one command that leaves the process, and
        that is not a packaging failure: the trainer is PyTorch and
        stable-baselines3 driving the C++ environment through the voxelenv
        module. Embedding libpython would not remove that dependency, it
        would pin the exe to one interpreter's ABI. kestrel checks the
        imports first and names the pip command if one is missing.

Video support is optional. Without OpenCV's videoio, `track` still runs over
an IMAGE SEQUENCE -- deterministic and diffable where a video decode is
neither, so it is the better thing to regression-test against.

THE OTHER TOOLS - not built by default
======================================

Everything below is still in the tree and still builds; it is simply off the
default target, so a plain build leaves you with one exe instead of a folder
of them. To get them:

    cmake -B build -DNAV_SIM_ALL_TARGETS=ON     the tools
    cmake -B build -DBUILD_TESTS=ON             the tools and the ctest suite
    cmake --build build --target voxel_gui      or just the one you want

  voxel_gui.exe    point-and-click front end: fly a synthetic forest
  voxel_sim.exe    the scriptable batch version of the same sim
  voxel_live.exe   the standalone build of what `kestrel sim` now runs

VOXEL_LIVE - the real map and planner over real depth
(`kestrel sim` and voxel_live.exe are the same code and the same flags)


VOXEL_LIVE - the real map and planner over real depth

Runs the SAME VoxelMap and TrajectoryPlanner as the simulator, over frames from
an actual camera. A menu opens: LIVE CAMERA / REPLAY A RECORDING / SIMULATED
FOREST, then START.

There is NOTHING to install for the live camera to work. librealsense is loaded
at runtime, so this exe needs no SDK to have been present when it was built. It
needs realsense2.dll to be findable when you RUN it, which it is if you have
installed the RealSense SDK or the Viewer.

  To check, with no camera plugged in, open PowerShell here and run:
      .\kestrel.exe sim --rs-check

  -> "librealsense 2.58.3 (realsense2.dll)"   good, LIVE will be enabled
  -> "could not load librealsense. Tried: ..."  copy realsense2.dll next to
     this exe, or put its folder on PATH. The list tells you where it looked.

In the view:  space pause   v first-person <-> overlay   s save PNG
              m menu        q quit

  DEPTH         what the camera returned. GREY IS NO RETURN, not far away.
  FIRST PERSON  the map from inside. Pale is UNKNOWN, drawn as fog, never air.
  OVERLAY (v)   the same voxels composited ON the depth image they came from.
                If they land on the trunks, the intrinsics, the frame
                convention and the pose all agree. This is the fastest check
                that the whole geometry chain is right.
  MAP SLICE     top-down. Green ring = how far obstacles are MARKED, orange =
                how far free space is CARVED. They are deliberately different.
  PLAN          faint = primitives that are flyable, green = the one chosen.

THE CAMERA IS ASSUMED TO BE HELD STILL. There is no odometry yet, so if you
walk around with it the map will be wrong. That is a missing subsystem, not a
bug in this program.


A menu opens. Click a world, choose Simulated stereo or Perfect (control),
and for the forest choose Open stand or Follow a trail. Then FLY. Keep this
whole folder together - the exe needs the DLLs beside it and reads worlds\
for the Hervanta / Tampere / Helsinki maps.

  IN FLIGHT
    space   pause
    r       restart the same run
    m       back to the menu
    q       quit
    - +     playback speed: 0.25x 0.5x 1x 2x 4x max
    v       FIRST PERSON <-> outside view of the voxel model
    [ ]     view distance of the voxel model: 20 / 32 / 44 / 60 m
    s       toggle voxel-model spin
    <- ->   rotate the voxel model

  WHAT YOU ARE LOOKING AT
    TRUTH + path        the real world, flown trail red, planned path green,
                        forest trails pale blue
    FIRST PERSON        the map from INSIDE, out of the aircraft's own eyes.
                        This is the default top-right pane; v swaps it for
                        the outside view. Pale is UNKNOWN, never empty -
                        where the map is wrong you fly into fog. It looks
                        short because it IS short: at 0.25 m voxels on a
                        12 cm baseline the map can only honestly mark
                        obstacles to about 5 m.
    VOXEL MODEL         the 3D map the aircraft actually built, as solid
                        blocks, with its flown path, its plan and the
                        heading it is currently commanding drawn into it.
                        Block colour is height RELATIVE TO YOU: red is at
                        your altitude and is what you would hit, green is
                        below, blue above.
    VOXEL MAP           a horizontal slice - grey means UNKNOWN, not empty
    DEPTH               what the camera returned; grey = no stereo match

  WORTH KNOWING
    Fly every world TWICE, once on stereo and once on Perfect. If it fails on
    Perfect depth the planner is at fault; if only on stereo, the sensor is the
    limit. That comparison found three real bugs in an afternoon.

    It wanders safely rather than arriving - no configuration reaches its goal
    yet. That is a known open problem, not a broken install.

    This build has no OMPL (no clean Windows port), so the forward planner uses
    a straight-line probe. The reactive layer does the obstacle avoidance and is
    unaffected.

  BATCH RUNS
    voxel_sim.exe is the scriptable version. One run you watched is an anecdote;
    sweep.sh runs every world x every seed and prints a table. Useful flags:

      cmake --build build --target voxel_sim
      voxel_sim.exe --world forest --seed 3 --truth --csv run.csv
      voxel_sim.exe --world osm --buildings worlds\helsinki_centre.txt --cell 0.5

    --truth   perfect depth instead of simulated stereo (ALWAYS run this too)
    --seed N  different generated world
    --csv F   per-step log for offline analysis
    --display live view


RL PATH-POLICY HARNESS
----------------------

The point is a comparison, not a model: a learned planner scored in the SAME
columns as the classical ones, on seeds it never trained on.

Double-click  baselines.bat    the non-RL side. random / freeM / goal / the
                               classical weighted score, all run through the
                               same environment the policy uses, so the
                               comparison is between planners and not between
                               two harnesses. Start here -- these are the
                               numbers a policy has to beat.

Double-click  train.bat        train. 16 workers, 10 M steps, stereo depth.
                               Expect 8-18 hours; it checkpoints as it goes,
                               so a crash costs minutes rather than the run.

Double-click  evaluate.bat     score a trained policy on held-out seeds.

First time only:
    pip install -r python\requirements.txt

The GPU will look idle during training and that is correct, not a
misconfiguration -- the bottleneck is environment steps, which are C++ on the
CPU. train.py --device cuda exists so you can measure that rather than take my
word for it. See docs/RL_HARNESS_PLAN.md section 11 for where CUDA would
actually pay (the depth renderer) and why the rest of the sim must stay on the
CPU (it is the code that flies).

CUDA (optional, and unverified)
-------------------------------

    cmake -B build -DNAVSIM_WITH_CUDA=ON -DNAV_SIM_ALL_TARGETS=ON
    cmake --build build --target cuda_depth_check
    build\Release\cuda_depth_check.exe

ONLY the depth renderer runs on the GPU. The map, the planner and the veto stay
on the CPU because they are the code that flies -- a second GPU implementation
of them would drift from what is deployed, and a policy would then be trained
against a world model that is not the real one.

THE KERNEL HAS NEVER BEEN COMPILED OR RUN by its author: it was written on a
machine with no toolkit and no GPU. cuda_depth_check is the gate. It renders
the same scene both ways and fails if they disagree by more than one voxel, and
it fails hard if the GPU invents a surface the CPU did not see. Run it before
trusting the GPU path; if it fails, build without CUDA and say so.

Expected payoff if it passes: the render is ~75 % of a step (46.8 ms against
~14 ms for everything else), so a 10 M-step stereo run should go from 8-18 h to
roughly 2-5 h on the same 16 workers.
